# fcode engine 2.3.6 → 2.3.8 delta (2026-08-14)

**Question:** does 2.3.8 (what the platform offers) differ from 2.3.6 (our
fleet pin, `tools/ENGINE_PIN`) in any way that changes GAME RULES, closing or
leaving open the "platform transfer UNVERIFIED" caveat on
`docs/prereg/SCREEN-v140vs142-2026-08-14.md` amendment A1.

**Verdict: RULES-IDENTICAL (transfer caveat closable).** Confidence rests on
static/dependency evidence, not on disassembling the compiled engine (see
"What this does NOT prove" below).

## What was checked

1. **PyPI changelog.** `curl https://pypi.org/pypi/fcode/2.3.8/json` — `description`
   is empty, `project_urls` is `None`, no changelog exists on the package
   index for either version. Method step 1 (published changelog) is a dead
   end for both releases.
2. **Wheel acquisition.** `.venv/bin/pip download fcode==2.3.8 --no-deps -d
   /tmp/fcode238` (did NOT touch the project venv, which stays pinned at
   2.3.6 per `tools/ENGINE_PIN`). Unpacked to `/tmp/fcode238/unpacked/`.
   Compared against the installed 2.3.6 tree at
   `.venv/lib/python3.13/site-packages/fcode/` and
   `.venv/lib/python3.13/site-packages/fcode-2.3.6.dist-info/`.
3. **Full package file-list diff** (2.3.6 installed tree vs 2.3.8 unpacked
   wheel, `__pycache__` noise excluded): only difference is the four hashed
   visualiser asset filenames under `fcode/data/visualiser/assets/*.{js,css}`
   (expected on any frontend rebuild) and pip-bookkeeping files
   (`INSTALLER`/`REQUESTED`, local-only). No files added or removed.
4. **Byte-for-byte diff of every `.py` file** in the package (all of
   `fcode/*.py`, `fcode/commands/*.py`, `fcode/data/*.py`): **only
   `fcode/commands/run.py` differs.** Every other file — including
   `fcode/_types.py` (the Python mirror of `GameConstants`: base costs, max
   HP, vision/action radii, `STARTING_TITANIUM`, `PASSIVE_TITANIUM_*`,
   `STORE_SIZE`, `MAX_TEAM_UNITS`) and `fcode/api.py` (the `Controller`
   wrapper — every method signature in the CLAUDE.md API reference) — is
   byte-identical.
5. **The `run.py` diff, read in full:** adds one Click option,
   `--mark INTEGER RANGE (default=100)` — "Print a progress marker every N
   turns (0 to disable)" — threaded through to `run_game(...)`. This is a
   **local `fcode run` CLI convenience flag** (controls stdout progress-line
   cadence), not a Controller API method, not a game constant. Confirmed live
   by installing 2.3.8 into an isolated temp venv (`/tmp/fcode238/tmpvenv238`,
   `python3.13 -m venv`, **not** the project venv) and diffing
   `fcode --help` / `fcode run --help` output against the project's 2.3.6:
   the top-level command list is identical; `run --help` differs by exactly
   the `--mark` line. This is the "known delta" s38's upgrade checklist
   already named ("`--mark` on 11 call sites").
6. **Maps.** No `maps/` directory ships inside the wheel in either version
   (maps are fetched separately via `fcode maps`, whose source —
   `commands/maps.py` — is byte-identical between versions). The repo's own
   `maps/*.map26` files (including `valkyrie.map26`, named in s38's checklist)
   are asset data outside the package and outside this delta's scope; nothing
   found here implies they need re-syncing for rules reasons.
7. **The compiled engine binary DOES differ.** `fcode_engine.cpython-313-darwin.so`:
   2.3.6 is 1,090,688 bytes (sha256 `803914f4…`), 2.3.8 is 1,088,432 bytes
   (sha256 `dc01815f…`) — different by ~2.2KB, consistent with a rebuild
   (build timestamps in the bundled SBOMs: 2026-08-05 vs 2026-08-14).
8. **SBOM diff (the load-bearing check for the compiled engine, since I did
   not disassemble it — see method step 2/constraint):** each wheel ships a
   CycloneDX SBOM at `*.dist-info/sboms/fcode_engine.cyclonedx.json`,
   generated by `cargo auditable` from the actual `Cargo.lock` used to build
   that `.so`. Diffed in full (59 lines of diff total, all inspected):
   - The **only dependency version change anywhere in the entire crate graph**
     is `zerocopy` **0.8.55 → 0.8.56** (content hash also changed
     accordingly) — a low-level zero-copy parsing/serialization utility
     crate, not a game-logic crate.
   - The actual rules engine crate, **`battlecode_titan@0.1.0`** (local path
     dependency, `engine/rust/`) — the crate the 2026-08-10 engine-source
     research (`docs/research/engine-source-crash-and-launcher-2026-08-10.md`)
     disassembled for cost/radius/mechanic facts — shows the **identical
     bom-ref and version string in both SBOMs**.
   - Every other one of the 54 components (all registry crates) is
     unchanged in version and content hash.
   - Only the top-level `fcode_engine` crate version, build timestamp, and
     SBOM `serialNumber` differ, as expected for any rebuild.

## What this does NOT prove

`battlecode_titan` is a **local path dependency**, not a registry crate, so
`cargo auditable` records no content hash for it (only registry crates get a
`Cargo.lock` checksum) — its unchanged version string is consistent with
"no change" but does not rule out an unpublished source edit that didn't bump
its internal Cargo.toml version. Per the task's explicit instruction, I did
**not** attempt to resolve this by disassembling/diffing the two `.so` files
directly (that remains the one thing that would make this airtight — a
symbol-level diff of `battlecode_titan`'s compiled functions across the two
binaries, the same technique used in the 2026-08-10 engine-source doc).

## Secondary finding (not part of the delta, flagging because it bears on
## method): local `fcode run` matches are NOT reproducible even within one
## engine version

I attempted a stronger empirical check — running the same bot pair
(`bots/_v234retire60` vs `bots/_x3r0v142`), same map (`valkyrie.map26`), same
`--seed 424242`, once on 2.3.6 and once on 2.3.8, and diffing the JSON result.
First pass (`--tle 10`, default) diverged hugely, but `--tle` is a wall-clock
CPU budget, which is a known confound. Re-run with `--tle 0` (unlimited, no
wall-clock cutoff) **still diverged** (240 vs 175 turns). As a control, I then
ran **2.3.6 against itself** twice, same seed, same `--tle 0`: results
diverged just as much (240 vs 163 turns) — and with `PYTHONHASHSEED=0` fixed
on top, a same-engine repeat run even flipped **which side won** (A vs B).
**This instrument fails its own same-version control**, so it cannot be used
to detect a cross-version rules delta (the noise floor swamps any possible
signal) — I did not pursue it further, but it's worth a note for anyone
relying on local `--seed` reproducibility elsewhere (e.g., any prereg
assuming a fixed-seed local run is replayable). Files under
`/tmp/fcode238/matchtest/` if anyone wants the raw JSONs; not committed
(scratch, per task instructions — commit nothing).

## Classification

| Difference | Class |
| --- | --- |
| `--mark` flag on `fcode run` | CLI-only |
| Visualiser JS/CSS asset hashes | Assets (frontend replay viewer) |
| `zerocopy` 0.8.55→0.8.56 | Build dependency (non-rules crate) |
| Everything else (Controller API, GameConstants, all other CLI commands, `battlecode_titan` version) | Unchanged |
| GAME RULES (constants, costs, cooldowns, radii, mechanics) | **No evidence of change found** |

## Verdict

**RULES-IDENTICAL (transfer caveat closable)** — on the strength of: (a) the
Python-side `GameConstants` mirror and the entire `Controller` API surface
being byte-identical, (b) the only functional Python/CLI change being a local
progress-marker flag unrelated to gameplay, and (c) the SBOM showing the
compiled engine's entire dependency graph unchanged except one non-rules
utility crate patch bump, with the actual rules crate (`battlecode_titan`)
showing no version change. This is strong static evidence, not a disassembly
proof; if Magnus wants it airtight, the remaining step is a symbol-level diff
of the two `.so` files' `battlecode_titan` code (not attempted here, per
task scope).
