# The replay corpus: ask it, don't rebuild it

**Built 2026-08-09 (session 22, research arm), on Magnus's direct call.**
**Version tag:** live **v89 "Eir 9c hivethaw (rollback)"** = `bots/_v100hf`,
md5 `9e85cae5`, tree hash `4558be91`.

## Why this exists

`replay_archive/` had grown to **3,831 files / 1.2 GB** while **the largest
replay-based read in the repo was 219 games** — most decodes were 5-35 games.
Yesterday's entire research output was explicitly *"ZERO replay downloads"*: six
deliverables, all on free `match info` metadata, with a 1.2 GB corpus sitting
unread on disk.

Nobody was wrong. Each decode was hand-written for one question, and the HANDOVER
records why that felt rational: *"session scratchpads DIE with the session — the
decoder scripts must be regenerated by a fresh analyst; budget ~10 min for that
on first use."* Paying 10 minutes to answer one question at n=9 is a fair trade.
Paying it to answer at n=3,831 is a much better one, and it costs the same.

**A whole-archive pass takes about three minutes.** This directory makes that
pass reproducible, and its output committed, so a session queries the corpus in
seconds instead of re-deriving it.

## Sync it at session start — this is the one you want

```bash
.venv/bin/python tools/corpus/sync.py          # decode only what is new, append
.venv/bin/python tools/corpus/sync.py --check  # report drift, change nothing
.venv/bin/python tools/corpus/sync.py --no-net # replays only, no fcode calls
```

**The archive grows ~80 replays/hour** while the archiver monitor runs (measured:
+160 files in two hours on 2026-08-09), so a corpus carried over from the last
session is materially stale and an overnight gap leaves a quarter of it
undecoded. Sync folds in only the new files: **200 replays + 55 ladder game rows
in 39 seconds**, against ~19 minutes to re-decode everything.

`corpus/decoded.txt` is the ledger of what has been folded in — the source of
truth for "what is new", rather than inferring from the tables, because a file
that legitimately produces no rows would otherwise be re-decoded forever.

**Fresh clone?** Only the `.tsv.gz` copies are committed. `gunzip -k corpus/*.gz`
then run sync, or just run sync — it rebuilds what it needs.

## Full rebuild — only when a DECODER changed

```bash
.venv/bin/python tools/corpus/build_corpus.py --force    # re-decode everything
.venv/bin/python tools/corpus/build_corpus.py --no-net   # skip the fcode calls
```

Stage costs: replay decode ~3 min each for throws and builds; ladder metadata
~4 min (487 paginated `match info` calls, free channel, **zero replay
downloads**). `corpus/manifest.json` records archive size, git sha, row counts
and the reconciliation rate at build time, so **staleness is detectable rather
than assumed** — compare `archive_replays` against `find replay_archive -name
'*.replay26' | wc -l`.

### `join.tsv` is the load-bearing one

A replay knows only "team 0" and "team 1". `join.tsv` maps each archived file to
the opponent name and to **which index is us** — the key that turns 58,251
anonymous throw events into *"Ouroboros has never thrown a builder against us"*.

**It passes the reconciliation test.** The standing rule from the tape
(2026-08-09) is that every join onto platform metadata must reconcile before a
verdict consumes it — `teamXRating` looked right for a day and was a live join.
Here the seat is derived from `winnerSide` + `won` in the free metadata, and must
then independently predict the `winner` field recorded **inside the replay
binary**. Rows that disagree are dropped, not kept.

```
1,155 of 1,155 testable rows agree — 100.0000%.  0 dropped.
```

Coverage: 1,165 of 3,831 archived files map to one of our ladder games. The other
2,666 are unrated matches and other teams' games — decodable, but unattributed
until someone pulls their `match info`.

## Worked example

Every number in `docs/research/late-game-doctrine-2026-08-09.md` came from these
five files and nothing else. E.g. "we build 0.2 turrets per game in r200-300 and
the field builds 2":

```python
import csv, collections
J = {r['file']: r for r in csv.DictReader(open('corpus/join.tsv'), delimiter='\t')}
acc = collections.Counter()
for r in csv.DictReader(open('corpus/build_agg.tsv'), delimiter='\t'):
    j = J.get(r['file'])
    if not j or r['band'] != 'r200-300':
        continue
    who = 'US' if r['team'] == j['our_team'] else 'THEM'
    acc[(who, r['metric'])] += int(r['n'])
```

## THE FOUR TRAPS — all four cost me real time today

1. **`placeEntity` is re-emitted on rotate.** `rotate()` re-emits a gunner that
   already exists, so counting every `placeEntity` inflates gunner builds ~3x
   (measured earlier: 1,315 of 1,915 gunner "places" in a 40-game sample were
   rotations, against 0 for every other kind). **A build is the FIRST
   `placeEntity` carrying a given entity id.** All decoders here guard it.
2. **`updateHp.delta` is a 64-bit two's-complement varint.**
   `18446744073709551609` is `-7`, not a large positive. My first throw census
   used a `1<<32` correction, which silently produced **exactly 0 core damage
   across 11,895 insertions**. I caught it because an exact zero is a bug
   signature, not a finding. **Prefer `BuilderAttack` (Update field 13) over HP
   arithmetic** — it is per-bot and unambiguous, and it is what these decoders
   use.
3. **Launcher throws emit no `FireTurret`.** A throw is a `moveBuilderBot` whose
   `to` is more than one tile from `frm`; thrower = a launcher alive at **d² ≤ 2
   of the pre-throw tile, diagonals included**. Consequence: a throw that lands
   exactly one tile away is indistinguishable from an ordinary step and is
   **undercounted**. Throws with launchers of both teams in range (937 of 58,251,
   1.6%) are marked `UNATTRIB`, not guessed.
4. **The archive is not a random sample of the field.** It is dominated by our
   own games; per-opponent coverage runs 8-23 matches. "Team X never does Y"
   always means "never against us, in N archived matches". Say the N.

5. **`econ.tsv`'s `shots` column is ZERO IN EVERY ROW — and a zero looks like a
   finding, not a bug.** Verified 2026-08-09 (s23): **25,530 rows, sum = 0.**
   `tools/corpus/replay_econ.py:109` declares the column and then does
   `elif unum == 12: pass` — *"fireTurret (unattributed)"*. Every **other** column
   in that file is populated, so nothing about the file looks broken. **Ask the
   corpus "how often do we fire?" via `econ.tsv` and it answers 0.**
   **USE `build_agg.tsv` WITH `metric == 'shot'` INSTEAD** — that is the correct
   source and it is what every shot figure in the s23 docs came from (US 97.7
   shots/game against the field's 258.5). Found by the builder arm while
   independently reproducing a research number, which is the only reason it
   surfaced at all. Not yet fixed in the decoder: existing rows would stay
   stale-zero until a full re-decode, and a 3-minute archive pass needs announcing.

## What this does NOT give you

Per-round titanium, ammo balances, and cooldowns are in `updatePlayers` but are
not extracted here. Damage attribution per source is deliberately absent — the
v72 bleed decode measured `replay_lib`'s built-in split mis-crediting a builder
with 5,359 damage whose true figure was 1,598. If you need damage, recompute it
from `fireTurret` keyed by shooter position, and treat builder attacks as the
residual.
