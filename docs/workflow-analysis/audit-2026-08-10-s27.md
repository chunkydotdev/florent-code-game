### What the current legs can actually resolve, on the primary currency

Computed from `scratchpad/loki1base/full.json` — the LOKI-1 leg, 384 games, 192 paired

Paired `SE(Δ) = sqrt(disc)/n = sqrt(p_disc/N)`. MDE at 80% power, α=0.05 two-sided,
= `(1.96 + 0.8416) × SE`:

| leg size (fixtures/arm) | MDE on **core-kill** | MDE on win rate |
|---|---:|---:|
| 120 | 16.4pp | 9.0pp |
| **240** (LOKI-10 as fired) | **11.6pp** | 6.4pp |
| 384 | 9.2pp | 5.1pp |
| **480** (LOKI-9 as fired) | **8.2pp** | 4.5pp |
| 960 | 5.8pp | 3.2pp |

**Two things worth having.** (1) At the effect sizes the Loki line actually produces
(LOKI-1 moved core-kill +26.6pp), 240–480 fixtures is ample; the 19% finding is
answered by practice. (2) **`core_kill_share` is a NOISIER paired statistic per game
than win rate** — it flips on 41.1% of fixtures against win rate's 12.5%. Switching
currency did not buy power. It bought a bigger effect, which is a different and better
reason to have switched, and it should be stated that way rather than as "the currency
is more sensitive".

**Verification of the leg identity, so this is not a number used somewhere else:**

## B. Currency integrity — **the primary finding**

### B1. Neither currency is implemented anywhere

```
grep -rn "core_kill_share" --include='*.py' .    -> 0 implementations
grep -rn "time_to_core_kill" --include='*.py' .  -> 0 occurrences, anywhere
```

Every hit for `core_kill_share` in `.py` is prose: a docstring at
`tools/loki9_facing.py:5` and a comment block replicated into every bot copy
(`bots/_v124loki8/doctrine.py:1367-1368, 1434-1437`). `time_to_core_kill` — the declared
SECONDARY_CURRENCY at `PROGRAMME.md:11` — does not appear in a single line of Python.

The tools that produce the paired p-values decide on **win rate**:

* `tools/reprice.py:64` — `grouped[...][r["cell"]].append(bool(r["ourwin"]))`. Hardcoded.
  There is no `--metric`. Every reading this tool has ever produced is a win-rate reading.
* `tools/mech_battery.py:205-211` — prints "SAFETY ARM (win rate…)" and nothing else
  whole-game. It records `cond` and `turns` in the JSON, so the currency is *derivable*,
  but the tool never computes it.
* `results.tsv:1` — the decision ledger's header is
  `commit  winrate  ci_low  ci_high  n  status  description`. **There is no column for
  the primary currency.** The two most recent ship rows carry win rates (`_v115dodge`
  0.870, `_v124loki8` 0.600) — the statistic `PROGRAMME.md:12` says is not a verdict.

### B2. Three denominators are in live use, and they disagree in SIGN

| # | definition | where it is used |
|---|---|---|
| (a) | core kills / **all games** | `bots/_v124loki8/doctrine.py:1434-1437` ("core_kill_share 12/15 = 80%"); `tools/ceiling.py:96` `kill_rate` |
| (b) | core kills / **our wins** | `tools/ceiling.py:97` `conversion` |
| (c) | **our kills / (our kills + their kills)** | `docs/coordination.md:19539-19545` — the v102 ladder verdict; reproduces exactly (32/(32+24)=0.571, 28/(28+25)=0.528, 46/(46+49)=0.484) |

Computed on the **same 384 games** of the founding LOKI-1 leg:

| definition | v92 control | LOKI-1 variant | delta |
|---|---:|---:|---:|
| (a) kills / all games | 0.562 | 0.828 | **+26.6pp** |
| (b) kills / wins | 0.647 | 0.919 | **+27.2pp** |
| (c) ours / (ours + theirs) | 0.923 | 0.909 | **−1.4pp** |

**Under definition (c) — the definition used to price v102 on the ladder — the result
that founded the entire Loki programme reverses sign.** `PROGRAMME.md:41-44` cites that
result as the reason `WIN_RATE_IS_VERDICT: no`; `PROGRAMME.md:52` makes "the Loki curve
crosses Eir on the primary currency" an exit condition of the programme. Which curve
crosses depends on a denominator nobody has written down.

### B3. The published headline reproduces under no denominator

`PROGRAMME.md:42-43` and `coordination.md:16278` publish "core-kill share **61%** vs
**91%**". From that leg's own `full.json` (n=192/arm; control 108 kills, 9 conceded,
167 wins; variant 159 kills, 16 conceded, 173 wins):

```
k/all           0.562 / 0.828
k/wins          0.647 / 0.919      <- closest
k/(k+their k)   0.923 / 0.909
k/(any core death)  0.923 / 0.909
k/(losses + k)  0.812 / 0.893
```

**None gives (0.61, 0.91).** The 91% is defensible as k/wins (91.9%); the 61% is not
(64.7%). Per-opponent means do not recover it either (mean k/all 56.3%, mean k/wins
65.1%). This is D16's fault inside the programme's own founding number.

### B4. What to do about it

One function, one definition, in one place — added to `reprice.py` as a `--metric`
so the paired estimator and the currency are the same code path, and the definition
pinned in `PROGRAMME.md` as a parsed field. Until that lands, **no two LOKI iterations
have been compared on the same statistic**, and `COMPARE_AGAINST: previous_line_iteration`
is not enforceable.

instead of chewing through the screen — so screening treatments are *flattered*, and
against probe sentinels (pass-through line) the same treatment reads as worthless. The
sign of a screening verdict depends on the probe's turret mix.

### Unresolvable verdict classes on the selected pool

| class | status |
|---|---|

| non-core heal | **UNRESOLVABLE** — nothing but our core is ever damaged, so heal has no event to act on |

## What is adequate, stated plainly

Not everything here is broken, and saying so is part of the job.

* **Statistical power at current leg sizes is adequate** for the effect sizes the Loki
  line produces. Nobody needs to re-run LOKI-9 or LOKI-10 for want of n.
* **The paired design is correct** and `reprice.py:59-64` handles duplicate fixtures
  properly — a real trap, correctly avoided.
* **`gate.py`'s programme, determinism and pool-identity checks are non-vacuous** — I
  fired all three today.
* **`ship_watch` and `slot_rule` are the best-instrumented things in the repo**:
  mutation-tested, cross-implementation, non-vacuous in both directions. The only
  problem with them is that the boot command does not run their tests.
* **The mill is producing.** 26 versions, 26 legs, 13 preregs, 4 behaviour ships in 24h.
  The cadence signal is real but the analysis signal is largely one batch generator.
